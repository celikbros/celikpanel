# Managed BIND V3 deletion and management-absent reboot — 2026-09-26

This is a bounded P0.4/P0.5 observation for constitutional invariants 1, 2, 3 and 6. It used fresh disposable Arch primary and Debian 13 secondary QEMU guests. The Debian peer ran native BIND without Panel or Agent. No installed CelikPanel server was changed.

The first real `SyncDNSZoneV3` deletion trial exposed a service-availability defect. The primary published a catalog without `s1-kill.test`; the secondary transferred catalog serial 2 and removed the native zone. Its DNS answer was `REFUSED`, which the Agent correctly did not count as proof of peer deletion. The Agent then tried to roll the primary back to catalog serial 1; paired proof failed while the peer was at serial 2, and the Publisher stopped primary `named.service`. This was a failed acceptance attempt, not a DNS success. Its evidence archive is `/var/tmp/cp-v3-delete26-failure-evidence.tar.gz`, SHA-256 `405cd00e207573deb603e1d0f650f114de316ddd17c0ff2d85b2c55ae828a8a7`.

The correction binds local deletion verification to the immutable BIND catalog receipt and its declared local address. It requires matching native catalog AXFR serial/member set plus empty deleted-zone responses over UDP and TCP; `REFUSED` alone still cannot prove deletion. A rollback that restores the prior pointer, daemon reload, durable state and local authority but cannot prove the peer now reports a typed peer-unverified condition and leaves native BIND running. Optional `rndc notify` failure cannot override a successful exact peer proof. Existing DNS engine state v2, zone-sync v3, service-mutation and BIND generation schemas were not changed; no new recovery authority or native service ownership was introduced.

After rebuilding the disposable Agent, Panel and fixture trigger from this tree, the same exact V3 deletion request `14b0d5712bca0f77e7556b215e9c2bb2` returned `pending_exact_operation`. Its persisted job remained `pending` at the exact propagation-pending phase; no second mutation was started. The primary state receipt pointed to the new generation and catalog serial 2. Both native BIND daemons remained active. The Debian secondary's `rndc zonestatus s1-kill.test` returned `no matching zone in any view`, and its native catalog showed serial 2. Direct primary and secondary SOA probes for the deleted name returned empty `REFUSED`. These observations establish actual native deletion, but the production Agent does not yet have an owner-verifiable remote peer-zone-state proof for this parentless zone, so pending is the honest outcome.

The primary Agent and Panel were then stopped and disabled **only in the disposable guest** and both guests rebooted. The Arch primary came back with native `named.service` active, Agent/Panel inactive and catalog serial 2; the Debian native secondary came back with `named.service` active, catalog serial 2 and no loaded `s1-kill.test` zone. The same pending mutation survived. Evidence is `/var/tmp/cp-v3-delete26-pending-evidence.tar.gz`, SHA-256 `25a215edf5f8565bdb3a9c761277b280d59f1712bac75d66a06b65cf4ed27a71`. The VM cell was stopped and torn down after capture.

This proves one managed V3 deletion can preserve native BIND service and deleted-zone state across a management-absent reboot while retaining an honest pending operation. It does not close P0.4 or P0.5: exact peer proof and operation completion, standalone Arch `rndc` control, automatic rollback under further faults, PowerDNS interoperability, owner edits, renewal and the complete workload/fault matrix remain open. The source checkout was not published as an installed-panel update.
