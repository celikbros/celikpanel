## What this does not prove

Fourteen passes, one run each, on one host, in disposable guests, all on the Debian 13 kill host, against one PowerDNS consumer version (4.9.17), one BIND version and two primary flavours. The V2 before-write edges passed once each; the owner inverse is still the owner-run path, not an automatic Agent recovery, and every V2 critical cell had a DNS outage by construction (8.8–27.2 s here, upper bounds). The retry-after-rollback directive case of the takeover passed once, with the two directives the fixture inserts, not with arbitrary owner configuration. The paired `rolled-back` and `intent` cuts happened before PowerDNS had a live database, so they add no evidence about rolling back a database the daemon has written into (batch 6b `c1`/`c2` remain the only such runs); zero metadata rows is an observation for two producers without DNSSEC, not a property of PowerDNS. The boundary held in fourteen cuts by two native sources (unit journals, file mtimes); that is evidence about these runs, not a proof for every boundary. All reboots were orderly; there was no power loss, no peer-unreachable paired cell, no Arch kill host, no CelikPanel-to-CelikPanel pair and no reinstall (row 14). The status-command exit-code difference between BIND and PowerDNS was observed, not explained. Commits made during the run were not tested. Nothing here changes the 268-runnable denominator, closes P0.4 or P0.5, or passes any acceptance-register row.
