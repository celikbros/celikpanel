## Deviations

- **`c1` ran without `--reboot-after-recovery`.** The controller refuses any reboot flag together with `--bind-rollback-after-target-started` (`run_cell.py` 5370–5377, `validate_reboot_settings`: "reboot steps require the socket flow without the independent handoff flags"), and the running-BIND adoption cell requires that precursor flag. The harness README ("Reboot during recovery") says the reboot steps apply to owner-inverse cells and to "adoption cells", which does not match the code. `guest_bootstrap.py run-prepared` does not refuse the combination; the controller would have exited 64 before any mutation. The combination was not attempted. The cell ran with its admitted flags, so reboot is not exercised for running-BIND adoption.
- **`c2` has no reboot** because its flow failed (see the cell).
- **A collection-script mistake in `c3`.** `collect.sh` read the watcher directory from the last line of `boot-monitor.log`, which after a reboot is the `watcher start rc=0` line, so it waited 60 s for a sampler that it could not name. The sampler had finished (`done` in `cp-b4-watch-boot2/timeline.log`); collection then ran normally. It was fixed before `c4` (the retained `build/fixture-tools/collect.sh` is the fixed version). No evidence was affected.
- **Sampler gaps.** Each post-boot sampler started when the host saw the new boot ID (~1 s after SSH readiness), so the first moments of each boot are not sampled. The sampler also missed short-lived journal phases (for example `c7`'s first `target-started`); `result.json` holds the boundary hashes.
- **Extra read-only capture in `c6`** (`extra-diagnostics-post-collect.txt`) after the automatic collection, before the guest was stopped.
- **Recovery status in non-enrolled cells.** `owner-post-state.txt` runs `recovery dns-switch-status` in every cell; in `c3`, `c6` and `c7` no launcher was enrolled (the bootstrap admits enrollment only for owner-inverse cells), so it exited 127.
- Every cell ran once. There was no re-run and no setup mistake requiring one.

## What this does not prove

Five passed cells on one host, Debian 13 only, one run each. The recovery kit is an unsigned local build enrolled as fixture work. There is no Arch coverage, no paired topology, no installed server, no power loss (every reboot was an orderly `systemctl reboot`), no owner-edit race and no continuous DNS probe. Reboot was exercised after recovery in `c3`, `c4` and `c7`, and before the owner command only in `c4`; it was not exercised for either adoption owner path (`c1` by admission, `c2` by failure). `c2` does not establish that the PowerDNS adoption owner path passes: the product side looked correct, but the cell's pass definition was not met. `c6` shows a real DNS outage after reboot in the tagged-build fault scenario; whether a production (untagged) Agent can reach the same "no `current` pointer" state is not shown. The earlier pass of that cell does not cancel this failure. `dns_outage` in `c4` (93.81 s) is an upper bound that includes a reboot, and depends on when the owner acts. The re-run exit 3 of a reconciled owner command remains a named gap. Package versions come from the live mirror. Nothing here changes the 268-runnable denominator, closes P0.4 or P0.5, or passes any acceptance-register row.
