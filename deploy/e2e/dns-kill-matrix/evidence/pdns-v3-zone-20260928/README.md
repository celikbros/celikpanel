# Fresh PowerDNS primary / BIND secondary: exact V3 zone lifecycle (2026-09-28)

Scope: D-025 invariants 2 and 4, P0.4/P0.5. This was a disposable Debian 13 PowerDNS primary (`192.0.2.10`) and panel-free Arch BIND secondary (`192.0.2.11`) in the `pdns-switch__intent__after-write__paired-primary__peer-reachable` fixture. It did not touch an installed panel, publish a release, or open the public paired-primary setup/RPC gate. The guest bundle was local and unsigned.

The first attempt used a parentless member, `s2-kill.test`. Add and edit reached terminal success. The exact delete request `4e5a3ed3b4f34d8c28630fd1c96ac92d` removed the native zone, but the secondary's empty `REFUSED` response did not prove remote absence. A separate same-request recovery kept the operation **pending** with `dns_peer_enrollment_required`, as recorded in [attempt10-ledger-pending.json](attempt10-ledger-pending.json). It did not issue a second delete. The production Agent was narrowed so a fresh V3 PowerDNS primary may combine a locally bound UDP/TCP empty `REFUSED` with its exact durable native tombstone; the remote peer still requires an authenticated native inspector or an authoritative parent-negative response. Other engines and topologies retain their stricter deletion proof. No schema version changed. A routine owner enrollment flow for this case remains unproven.

A fresh overlay used child `s2.s1-kill.test` under an authoritative parent. The exact switch request `eeaf718b824f70d95f80f76077cdb7c7` was cut at the fsynced `target-enable-intent` boundary with [systemd reporting signal 9](attempt11-systemd-cut.txt); a separate process reconciled the **same request** to `succeeded`. Four distinct, explicitly authorized V3 zone operations then reached terminal `succeeded` in [attempt11-ledger.json](attempt11-ledger.json): add `50fcbfeb2f2fd19be7faf30d088450b0` (generation 1, SOA `2026092801`), edit `1e17a1372a4ff245e1483290c0b8488e` (generation 2, SOA `2026092802`), delete `0bc536342f18e4acc5a94a7bf3fb3fc5` (generation 3, parent-authoritative NXDOMAIN on both), and re-add `16f63bbe4a17061e344bcefeae34e824` (generation 4, SOA `2026092803`). Both native servers returned the matching SOA and `www` A after add, edit and re-add; the edited-only `changed` A disappeared after re-add. The final [V3 engine state](attempt11-state.json) retained the same acquisition request. The ledger has no active request.

After these operations, Panel and Agent were disabled on the disposable primary. Both guests rebooted with new [boot IDs](attempt11-boots.txt). The [primary](attempt11-primary-services.txt) retained active/enabled `pdns.service` with inactive/disabled Panel and Agent; the panel-free [secondary](attempt11-secondary-services.txt) retained active/enabled `named.service`. The independent [primary SOA](attempt11-primary-soa.txt) and [secondary SOA](attempt11-secondary-soa.txt) still matched at `2026092803` after reboot. The tagged native test required root-owned, mode `0600`, boot- and request-bound authorization; it did not admit an ordinary product user or installed server.

This is one exact poststart cut and one paired zone lifecycle, not the full kill matrix. Parentless peer deletion without owner enrollment, public setup/RPC admission, ordinary owner enrollment, later fault points, owner edits, existing BIND-primary-to-PowerDNS migration, independent inverse, installed-panel update recovery and non-DNS workload independence remain open. P0.4/P0.5 are not complete. The disposable overlays were stopped through QMP and removed after evidence capture. Retained files are covered by [SHA256SUMS](SHA256SUMS).

## Corrections after intake (2026-10-10)

Checksum repair (2026-10-10): the `SHA256SUMS` of this directory had been committed with CR LF line ends, so `sha256sum -c SHA256SUMS` on a Unix system read every file name with a trailing carriage return and reported each listed file as unreadable. Every listed hash was correct: `tr -d '\r' < SHA256SUMS | sha256sum -c` verified all files before the repair. The line ends of the list were changed to LF (the hashes and file names are unchanged; the evidence files themselves, which are CRLF as collected, were not touched).
