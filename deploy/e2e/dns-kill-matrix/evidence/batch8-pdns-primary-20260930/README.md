### The seven failures: one wrong harness expectation, not a product deviation

The only failure in `c01`–`c07` (`result.json` `fresh_primary_v3.failures`, verbatim, identical in all seven):

```
pair: primary udp www A ['192.0.2.10']
pair: primary tcp www A ['192.0.2.10']
```

**The harness expected the wrong thing.** `check_fresh_primary_pair` compares the primary's `www.s1-kill.test` A answer with `settings.dns_address` (`deploy/e2e/dns-kill-matrix/run_cell.py:11394` `local, peer = settings.dns_address, FRESH_PRIMARY_V3_PEER_IP`, judged at `run_cell.py:11415-11416` `if primary["www_a"][transport] != [local]`, at `916e1577`). The controller's DNS address on this guest is the QEMU user-network address `10.0.2.15` (`raw/fixture/controller-argv.json` `--dns-address 10.0.2.15`, set by `guest_bootstrap.sh` from the guest), while the zone's `www` A is the pair address `192.0.2.10`, which is exactly what the harness README pass definition requires ("the primary answers `s1-kill.test` SOA `2026083101` and `www` A `192.0.2.10` over UDP and TCP"). The primary answered `192.0.2.10` over UDP and TCP, the native BIND secondary answered identically (`fresh_primary_v3.pair.secondary == primary`, first attempt), and every other part of the pass definition held (below). This is not a setup problem that could be worked around without changing a pass rule, so it was not worked around: each cell was stopped with its overlays kept, and the run continued. Consequence: `complete_verdict`/`pre_reboot_verdict` failed, so **the requested reboots (`c01`, `c04`) and the zone lifecycle (`c04`) never ran** (`reboot_after_recovery.run: false`, reason "the complete pre-reboot verdict is not a pass (status is 'failed'); the reboot is defined only for a passing flow and was not run …"; `run_zone_lifecycle` runs only after `combined == 0`, `guest_bootstrap.py` `finish_fresh_primary_run`).
