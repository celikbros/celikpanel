# set8, 2026-10-10 (UTC): what v0.1.0-alpha.82 (the source tree of the published tag, built as the acceptance-licence test build under an alpha.81 label, not the signed release archive) does with a site's nginx vhost and PHP-FPM pool that the server owner edited by hand, on disposable Debian 13, Ubuntu 24.04 and Arch guests

A measurement record (a native baseline). It measures the "Result today" column of
`docs/audit/SITE-CONFIG-OWNER-EDITS-2026-10-10.md` §5 (and the first item of its §9) on real services. Nothing of the
product was changed; nothing was committed or pushed. The harness was set up to address only the guests (the driver's
requests carry the host-side address `127.0.0.1:<port>`); it was not set up to address an installed server,
celikpanel.net, the licence service or a certificate authority, and the five names were pinned to loopback inside the
guests (see "Network": the guests have outbound NAT and no traffic was captured, so this is neither isolation nor a
measured "no outside contact").
Every `result.json` carries `native_evidence: false`. It closes no P0 row and implements nothing of the audit's §7.

## Result in one paragraph

On all three platforms, in every one of the 40 vhost runs (10 per lab, four labs), the Panel replaced the owner's
edited vhost with its own text at the next Panel start, Panel restart or General-settings save: an added `location`,
a changed template directive, a whole replacement file and an added `include` were each gone (new inode, owner's
answer no longer served, nginx reloaded: worker PIDs changed and a `Reloaded nginx.service` line follows the trigger;
the journal's reload lines name systemd only, so that the Panel caused the reload is inferred), and a vhost the owner
had removed (file and enabled link) was recreated and served again. None of the Panel API answers read said so: the
Domains list, General, PHP and Dashboard answers were identical (parsed JSON, equal Content-Length) before and after in
all 48 runs with both readings (the Panel's screens in a browser were not looked at); Components changed in 3 runs
(arch run-a d3, debian13 run-a c1, ubuntu f) only to "Service state is unverified; run a fresh scan" on the setup
profiles (the cause was not examined; "the stored scan aging" is a guess, nothing in the answer names a vhost); no audit
entry was written in the 24 start/restart runs (a save writes only its own `domain.general.update`), and the only Panel
line about the vhosts is the start's `restored 3 hosted vhosts with one nginx validation and reload` (after a save the
Panel and Agent units wrote no line naming a site, vhost or nginx; their window holds only `http: TLS handshake error`
lines of the Panel and the driver's own `Getting pool config` lines of the Agent). A pool edit survived a Panel start,
but the Panel's pool save (answered 200 "Pool configuration updated") dropped the owner's directive and comment and PHP
served the old value again. With `chattr +i` on one vhost the Panel started and answered, its whole start batch failed
with one journal line, the enabled link of the locked site was absent after the start (present before; the journal
names only the failed file removal, so that the failed rollback removed the link is an inference), nginx was not
reloaded by the start, and the next nginx reload (run by the lab as a log rotation would) took that site out of service
(404/403) while the Panel's answers still showed it `active`. **D-022 verdict:
overwritten silently in every vhost and pool-save run; kept silently at Panel start for the pool; for `chattr +i`: the
file kept, the site silently broken at the next reload.** The audit's inferred table holds, with the corrections below.

1. **The Panel's own creation render differs from its own start/save render** (all three platforms, every site including
   the static one): created with `server_name set8-a.test;`, re-rendered at the next start or save as
   `server_name set8-a.test www.set8-a.test;` (`*/run-*/driver/steps/09-s0-sites/diff/creation-render-vs-start-render.diff`

   the sites, 16:52:28-33Z, so that text is the one written at creation). What follows for the audit's §8 is a conclusion, not a measurement: a
   plan to recognise alpha.82-written files by re-rendering "alpha.82's template" would have to include the
   creation-time variant, or untouched alpha.82 sites would land in `unknown-origin`.
2. **A settings save leaves no Panel or Agent journal line about the site, the vhost or nginx** (the audit says "same"
   success line for every render); the only trace is the save's own audit entry and nginx's own reload lines. The journal

## Method

Built from `git archive 2a0af8866` (= `v0.1.0-alpha.82`, tree `988ea2ea...`): `run-upd1.sh build 2a0af8866` in a disposable
clone, acceptance-test licence build, one job 15:42:07-15:47:11Z (`build/`). The installed baseline is commit
`9e12ed1aa903...` (tree `ff0d0eef...`, archive SHA-256 `fdb005cabcdaa78ff83fd97abbebeb7a0c98f1a23062db42eead5a33334af117`):
2a0af8866 with only `deploy/release-sequence-policy` changed (labelled `v0.1.0-alpha.81 / 81`, as set6/set7 did;
`build/cur/trees.txt` lists that one file as the only difference and counts 0 files of `cmd/`, `internal/`, `web/`
different; `build/cur/fixture-patch-baseline.diff` is the patch). The baseline commit exists only in the disposable
clone (`build/cur/fixture-commits.txt` also lists the unused upd1 refs good, defective, real-start and start-check; set8
installed only the baseline). Its Panel is built with the `acceptance_license` tag (every Panel start prints an
`ACCEPTANCE FIXTURE - NOT FOR PRODUCTION` line), so its licence code path is not that of the published binary. It is
not the signed release archive.
`run-upd1.sh prove` exit 0; dry runs of the three cells exit 0, no lab created (`build/`).

Each cell (`set8_trial.py` over set6's `Set6Trial`, steps unchanged): `set6-name-pinning` first (celikpanel.net and four
CA directory names to the guest's loopback, read back by the hosts file and the default lookup path, refused if any
product path existed; passed in all four labs), `preflight`, `origin`, `baseline-install`, `owner-login`, `license`
("not contacted: acceptance test build"), `setup` (waits at `access_dns`, `observed`, as in set6), `site` (set1's static
site). Then S0: two PHP sites A `set8-a.test`, B `set8-b.test` created through `POST /api/v1/domains/create`; the owner
uploads a probe page, an index page of their own and a page printing `memory_limit`; A's vhost bytes, inode, mode,
owner, `lsattr`, enabled link, pool file and `nginx -T` recorded. Final driver (Ubuntu, Arch, Debian run-b): then the
Panel is restarted once with no owner edit (lab preparation) and A's vhost read again = the start render.

Each run: **lab restore** (not an owner action) writes the reference text back (run-b/Ubuntu/Arch: the start render with
its owner, group and mode; Debian run-a: the creation render as `root:root 0644`), its enabled link, `nginx -t`,
reload. Then, as the owner: (stopped runs) `systemctl stop celikpanel-panel`; the edit, written into the same file
(same inode), `nginx -t`, `systemctl reload nginx`; the owner's answer is read on `127.0.0.1:80` with the site's Host.
Running runs wait 20 s and read again (the file was unchanged before the trigger in every running run). Trigger:
`systemctl start|restart celikpanel-panel` (waits for the reconcile journal line and the API), or
`GET`/`POST /api/v1/domains/{id}/general` with the values shown. After: file, `stat`, `nginx -T`
(`<lab>/driver/nginx-T/<sha>.txt`), journal of the Panel, Agent, nginx and PHP-FPM units since the run began
(`native/*-journal.json`), HTTP, and the API answers an owner sees (Domains list, General, PHP, Dashboard, Components
`/api/v1/managed-services`, `/api/v1/audit-logs`), before and after. Trigger 2 (save) is done with the Panel running:
with the Panel stopped while editing, its own start would render first. The template sets no `client_max_body_size`,
so scenario b changes the template's `index` directive.

Debian run-a used driver copy c (restore to the creation render): its classifier marked the runs "unknown" because the
Panel's bytes were the start render, not the creation render (run-a is kept as recorded; its `section.json` and
`result.json` notes still say `unknown`, and its g record says no vhost file was rewritten because that driver compared
inodes only); `tools/table.py` classifies every lab with both renders
and with the bytes the Panel wrote into the empty path in e1. Driver copy d (run-b, Ubuntu, Arch) adds the reference
restart, restores with the recorded owner/group/mode, and uses ctime as well as inode for "touched" in g.
