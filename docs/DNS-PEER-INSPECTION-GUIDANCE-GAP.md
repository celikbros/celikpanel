# DNS peer V3 pending-guidance audit — 2026-09-27

Scope: source review of the optional BIND and PowerDNS native deletion inspectors and the pending reason exposed after exact Agent-job reconciliation. No installed server was changed. This is a P0.4/P0.5 and D-024/D-025 review; it does not close either acceptance item.

## What the current evidence can say

An exact V3 deletion can retain a reviewed `dns_peer_inspection_unknown` reason when the owner-enrolled SSH inspection did not produce a usable authenticated response. Both native paths return that code for any `Inspect` error (`cmd/agent/dns_engine_peer_native_linux.go`, `cmd/agent/dns_engine_peer_pdns_linux.go`). The transport intentionally returns one `CodeUnavailable` for connection, host-key/authentication, SSH session, forced-command exit and output-overflow failures (`internal/dnspeertransport/transport_linux.go`). The PowerDNS reader can also fail on service identity, listeners, config, SQLite, control socket or a changing daemon (`internal/pdnspeerinspector/native_linux.go`); a forced-command exit folds those failures into the same transport code. The reviewed reason therefore means **inspection did not complete**, not that SSH, PowerDNS, a zone or transfer is known broken. The existing English/Turkish guidance is appropriately broad but should not imply a diagnosed service failure.

A valid authenticated response with `catalog_state=stale/unknown`, `member_state=present/unknown` or `native_state=loaded/unknown` reaches `dns_peer_native_unknown` after proof validation (`internal/dnspeerproof/proof.go`). That reason says absence was not established; it cannot assert the zone is missing or the native daemon stopped. The exact pending job, rather than the optional RPC field alone, controls Panel guidance (`cmd/panel/dns_sync_v3.go`, `cmd/panel/dns_peer_pending_guidance.go`). Unknown/older codes retain generic guidance.

The 27d BIND→PowerDNS native trial observed a transient `dns_peer_inspection_unknown` after native catalog serial 2 and an unloaded member were observed. A later authenticated read succeeded; recovery of the **same** V3 request completed. That sequence supports unknown inspection, not a proven cause. See `deploy/e2e/dns-kill-matrix/NATIVE-BIND-PDNS-PEER-STAGE2-20260927.md` after its final evidence update.

## Actionable-guidance defects and narrow correction contract

1. The source can identify local enrollment drift more precisely than it currently reports. Both `verifyCurrent` closures check exact attempt, peer enrollment and local native evidence together. At the first, post-SSH and final check, every closure error is converted to `dns_peer_owner_edit_unknown`. A changed/replaced enrollment then tells the administrator to reconcile native DNS instead of the pinned peer credential. Separate the local checks and return the existing `dns_peer_enrollment_changed` code for a proved enrollment recheck failure. Keep a changed ledger attempt or local DNS evidence in `dns_peer_owner_edit_unknown`. During publish/consume of the durable challenge, keep `dns_peer_journal_unknown` if the journal transition itself cannot be reconciled. Tests must exercise an enrollment swap at each boundary without accepting the proof or starting a second mutation.

2. Do not add a new “PowerDNS service failed” or “SSH failed” reason based only on current `CodeUnavailable`. A safe finer classification requires a versioned, bounded inspector result that can be attributed to the authenticated peer, with a reviewed enum, exact request digest and no raw command output. The transport must distinguish authenticated response bytes from connection/session failure before assigning a more specific reason. The Agent must recheck the same operation, enrollment and native evidence before recording it in ledger v1 `error_code`. Older schemas and ambiguous output stay `inspection_unknown`.

3. The owner guidance for `inspection_unknown` should name both practical checks without assigning blame: the primary administrator checks pinned SSH enrollment and access; the secondary owner checks the forced inspector's permission and its read-only native control/SQLite observation. The user resumes the **same pending publication** through the existing explicit recovery action. A status poll remains read-only. If an authenticated response says `loaded` or `stale`, guidance may refer to that observed state only after a versioned, current and exact-job classification; otherwise retain `native_unknown`.

## Required negative evidence before narrowing a reason

Exercise refused TCP/22, wrong pinned host key, rejected SSH user key, forced-command exit, overlong/malformed output, remote PowerDNS control-socket denial, SQLite inode swap, stale catalog, still-loaded zone, enrollment replacement before challenge and after SSH, journal consume failure, and loss of the exact Agent attempt. For every case assert the recorded bounded code, no raw stderr or secret in API/ledger, no terminal deletion, no second mutation from polling, and same-request recovery only when current evidence is rechecked. Native integration must also prove an ordinary transient inspection failure can recover without rewriting DNS or enrolling a different owner identity.
The first audit was read-only. The narrow enrollment classification below is now implemented; the proposed transport subcodes remain design only. A native recovery run is still required before claiming D-024 acceptance.

## Narrow source correction and evidence

The source now uses the existing reviewed `dns_peer_enrollment_changed` code when a current BIND or PowerDNS peer enrollment recheck fails. A changed exact ledger attempt or local native DNS evidence retains `dns_peer_owner_edit_unknown`. The check order is attempt, enrollment, native evidence; a failed earlier boundary prevents later checks from masking it. Both production inspectors return that classified result at the initial, post-SSH, pre-consume and final current-state checks. A failure inside historical challenge reconciliation or durable publish/consume remains `dns_peer_journal_unknown`, because the journal transition cannot be declared reconciled merely from its cause. Raw enrollment, SSH and native probe errors are never returned as the reason.

Affected invariant: D-025 evidence meaning and D-024 truthful owner action for P0.4/P0.5. The durable service-mutation ledger stays at v1; it already permits the reviewed code in its `error_code` field. Peer request/response v1 and journal v1 remain unchanged. A pending publication retains its exact operation and is resumed by the existing explicit recovery path after the owner checks enrollment; no poll or new request is authorized by this classification change.

Evidence: `go test -count=1 ./cmd/agent` passed on 2026-09-27. `TestPeerCurrentPendingCodeKeepsFirstFailedBoundary` proves ordering, existing bounded reason persistence and redaction of private details. The focused BIND/PowerDNS peer regression selection also passed. A native induced enrollment-swap trial has not run, and this correction alone does not close P0.4/P0.5 or D-024's full adapter matrix.

## Ordinary owner enrollment is still missing

The production Agent currently reads and rechecks `dns-peer-inspection-v1.json` or `pdns-peer-inspection-v1.json`; the only writers found in this tree are isolated E2E fixture scripts. Panel and translated error text tell an administrator to enroll the peer, but no reviewed ordinary product enrollment action is demonstrated here. This is a practical Stage 2 and D-024 gap even though the fixture channel can complete a deletion. An owner-facing path must obtain explicit peer-owner consent, pin the SSH host and client identities, install a bounded read-only policy, verify the exact secondary engine, and support revocation and rotation without requiring a remote CelikPanel API. It must show the primary owner the current prerequisite and a same-request recovery action, with negative tests for changed keys, policy and permissions. No installed server enrollment or native trial of that product path is claimed.
